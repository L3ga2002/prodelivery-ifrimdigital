## 1. BFCache create/edit/assign — prima prioritate

Finding static al reviewerului: useOrderCreationRecovery, useOrderEditingRecovery si useOrderAssignmentRecovery asculta storage, dar nu au protectie pagehide/pageshow si revalidare cookie similara useOrderStatusRecovery. AuthContext verifica /auth/me la mount; BFCache poate relua componenta fara un mount nou. Acknowledge este local, deci headerul comparativ care protejeaza serverul nu este suficient pentru confirmarea/curatarea locala a unei intentii straine. create.deactivate() sterge draftul; suspendarea trebuie separata de logout/deactivate.

Primul pas: reproducere RED intr-un fisier NOU, cu deferred finit si timeout, fara bucle while(await Promise.resolve()). Scenariu: pagina A suspendata -> cookie schimbat in B -> pageshow persisted -> ACK/retry inainte de /auth/me. Findingul este candidat pana la reproducerea executata; nu este declarat defect runtime deja testat.

Acceptare:
- ACK/retry/admission blocate pana la revalidarea actorului; identitatea din header ramane comparativa, nu autentificare alternativa.
- Mismatch,401,403,503,timeout si offline nu sterg intentia si nu confirma succes strain.
- Draftul exact si UUID-ul se pastreaza la suspendare; rezultatele requesturilor dinaintea suspendarii nu se publica ulterior.
- Revalidarea actorului corect permite numai fluxul prevazut de protocol; fara POST automat sau ID nou.
- Listenerii se curata corect la unmount/StrictMode; regresia useOrderStatusRecovery este verificata ca flux adiacent.
- Dovada browser BFCache cere pageshow.persisted===true. Evenimentele simulate si navigarea cu reload se raporteaza separat.

Fisiere candidate, nu mandat de editare in masa: frontend/src/hooks/useOrderCreationRecovery.js, useOrderEditingRecovery.js, useOrderAssignmentRecovery.js; lib/orderCreationRecovery.js, orderEditingRecovery.js, orderAssignmentRecovery.js; context/AuthContext.js numai daca reproducerea cere o schimbare acolo. Hookul status existent este precedent de inspectie, nu rescriere.

## 2. Curse intre servicii — owner backend separat

Nu se repeta edit–edit, assign–assign, status–status ori pregatire–edit deja acoperite. Matricea noua priorita:
1. Editare versus alocare, aceeasi revizie initiala.
2. Realocare inainte de acceptare versus ACCEPTED al vechiului driver.
3. Livrare A versus alocare B pentru acelasi driver.

Bariere deterministe dupa snapshot, finite, ambele ordini de castig. Pentru aceeasi comanda/revizie initiala exista un castigator sau conflict explicit. Pentru A/B sunt admise rezultatele seriale valide; eliberarea lui A nu poate sterge rezervarea lui B. Receiptul, auditul, creditul unic si claimurile sunt verificate in Mongo dupa ambele raspunsuri. Replay nu schimba business state.

Se folosesc serviciile reale si Mongo izolat; apoi, unde e necesar, dovada HTTP cu identitati distincte. Mocks de colectii sau config global nu sunt prezentate ca dovada de concurenta reala intre roluri. Fixurile minimale urmeaza numai unui RED demonstrat; originalele testelor raman intacte.

## 3. Restart al procesului API

Gap verificat read-only: testele existente de restart reinstantiaza serviciul in acelasi proces Python; browserul anterior face reload, nu restart API. Noul harness trebuie sa reataseze explicit DB sintetica detinuta dintr-un manifest, fara reset/reseed al intentiei.

Doua frontiere separate: dupa ledger pending admis, inainte de efect; dupa commit durabil fara ACK. Bariera este numai in wrapperul QA, cu codul business real. Oprirea necesita verificarea PID/script/executabil/port/dbpath; proces nou, aceeasi DB retinuta.

Acceptare: acelasi client_operation_id/digest/request_id; lookup read-only si resume bodyless; cel mult un efect, un audit si o schimbare de revizie. Marker admission disabled in fixture refuza intentia noua, dar nu inchide recovery pentru cea deja admisa. Fara fallback legacy, payload reconstruit sau intentie noua. Nu implica restart Mongo, failover ori date reale.
